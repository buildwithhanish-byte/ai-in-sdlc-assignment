Task 2: Reliable invoice submission to PayEx

Status: Proposed architecture decision; production adoption depends on provider capability checks.
Date: 24 October 2026

Prepared with AI assistance, as recorded in the AI augmentation log. This decision describes the planned production design; it does not claim that the integration has been implemented or tested.

1. The problem

When PayEx times out, we do not know whether it accepted the invoice. Sending it again could create a duplicate, but not sending it again could leave the invoice unsubmitted. We need a durable record of every approved invoice and a safe way to resolve uncertain submissions.

The scenario has six engineers, including two new to the codebase, with a weekly on-call rotation. It expects about 40,000 invoices a month, with 60% in the final three working days and a peak near 80 approvals a minute. PayEx times out at 30 seconds and may have accepted a timed-out request. Approval actions must remain auditable for seven years. The current application uses in-memory storage; persistence, the worker and PayEx integration are proposed additions.

2. Proposed decision

Use a transactional outbox in Azure SQL and a background worker, together with a stable submission key. Save the invoice approval, audit event and instruction to submit in one database transaction. The worker processes that saved instruction independently of the user's request.

The outbox is a durable to-do list. It protects against approving an invoice and then forgetting to submit it after a crash. It does not, by itself, prevent PayEx from processing a repeated request twice.

Keep the initial design small: one SQL-backed outbox and one worker component, with safe work claiming, monitoring and a runbook. Multiple worker instances would require coordinated claims and concurrency controls. Do not add Service Bus to this path merely because it is available. Revisit that choice if measured needs justify it.

3. What exactly-once means here

The desired outcome is one PayEx submission effect for each approved invoice operation. Multiple network attempts may occur. A successful submission reference is evidence of acceptance, not proof that an invoice has been paid.

The supplied facts are insufficient to guarantee exactly-once processing at PayEx. Before enabling automatic retries of uncertain requests, verify the provider's key scope, retention window, handling of concurrent requests and repeated keys, and behaviour when a key is reused with a different payload. Establish whether authoritative lookup or reconciliation by operation identity is available, including how delayed visibility and in-flight requests are handled.

If those guarantees are unavailable, hold uncertain submissions for investigation. This avoids blind retries but delays completion. A local dedupe table or outbox cannot remove this trade-off. Reliable eventual submission also assumes the provider recovers and the request is valid; a terminal rejection must remain visible rather than being retried forever.

5. How the chosen design works

  1. Authenticate and authorise the approver. Use a conditional state/version check to prevent conflicting approvals.
  2. Assign a stable operation identity for the invoice and approved version. Enforce its uniqueness and retain the payload snapshot. A retry must not generate a fresh key or silently change the payload.
  3. Commit the approval, audit event and outbox intent together. If commit acknowledgement is lost, resolve durable state with the same identity. Do not assume rollback; permit a retry only after the transaction is resolved and the invoice remains eligible.
  4. The worker claims due work with an expiring lease and records attempt information. Keep the PayEx network request outside the database transaction.
  5. On confirmed acceptance, save the PayEx reference and mark submission Confirmed. On explicit terminal rejection, mark Failed and expose the reason. On a timeout or crash around sending, treat the outcome as Unknown.
  6. Resolve Unknown using verified provider capabilities. Retry the same key and payload only within the provider's safe deduplication conditions. A lookup returning no result is not automatically proof of failure: rule out delayed visibility and an in-flight request before resending.
  7. Show approval status separately from submission status. Track Pending, Unknown, Confirmed and Failed submissions and keep the transition history.

An expired lease permits recovery work; it does not prove the previous request failed. Provider duplicate protection remains necessary if attempts can overlap. Seven-year approval audit retention also needs access controls, retention policies and retrieval checks; merely inserting a SQL row is insufficient.

6. Challenge: a simpler design for a small team

The discussion challenged the recommendation with: “I prefer idempotency keys with a dedupe table because our six-person team should avoid the complexity of a worker.”

The recommendation stayed with the outbox. A smaller design must still recover approved-but-unsent invoices and resolve uncertain requests. A process that scans Pending records and safely retries unfinished work takes on much of a worker's responsibility. The strongest objection remains valid: the worker adds support burden. Keeping the design small, rehearsing recovery and providing a clear runbook are conditions of this recommendation.

This exercise is evidence that the agent did not change its answer solely to match the stated preference. It is not proof that the recommendation is objectively best.

8. Build and running costs

The main additional build work is the outbox schema, transaction boundary, worker, work claiming, retry and Unknown handling, status display, monitoring and failure tests. SQL persistence and approval audit retention are shared production requirements across all three options; they should not be charged only to the outbox choice.

Illustrative planning estimate, not measured delivery evidence: once basic persistence exists and the PayEx contract is known, allow roughly 5-8 engineer-days for the outbox/worker flow, 4-7 for recovery and provider integration behaviour, and 4-7 for failure tests, monitoring and the runbook: 13-22 engineer-days in total. This is an agent estimate for comparison, not a commitment. It excludes initial persistence, production identity, seven-year retention implementation, procurement and provider waiting time. Two new engineers, unfamiliar infrastructure or an inadequate provider API could increase it substantially. Validate the range with a small integration spike and a team estimate.

Running costs include worker compute, incremental SQL storage and I/O, telemetry, audit storage and on-call investigation time. Optimistic reconciliation also needs scheduled compute, provider data access and investigation time. Exact currency figures are not available: deployment region, existing capacity, pricing tier, retention volumes and provider charges have not been selected or measured.

A useful monthly cost model is incremental compute + database capacity/storage + telemetry and audit retention + provider request charges + support hours. Use the deployment estimate and provider contract for the first four, then measure support effort during a pilot. Do not mistake 40,000 invoices for 40,000 API attempts; retries and status lookups add requests.

As a capacity thought experiment only, 80 submissions per minute with every request occupying 30 seconds implies about 40 concurrent in-flight requests just to match arrivals. This is not a benchmark or a recommended concurrency setting. Actual sizing needs measured latency, provider rate limits, retry behaviour and backlog-draining headroom.

9. What would make this decision change?

  • PayEx cannot provide safe duplicate handling or authoritative outcome resolution: stop treating exactly-once as a deliverable guarantee and revisit the integration, provider agreement or business requirement.
  • A prototype demonstrates a simpler approach with equally reliable crash recovery and acceptable support effort: compare it again rather than retaining the worker by habit.
  • Load tests or production evidence show sustained backlog beyond the agreed service target despite safe tuning: revisit capacity, processing topology and whether messaging would help.
  • Unknown outcomes or manual support exceed an agreed operational budget: improve provider reconciliation or reassess the integration before increasing volume.
  • New consumers, ordering requirements, provider contract changes or deployment constraints alter the trade-offs: review the decision and rerun relevant failure tests.
